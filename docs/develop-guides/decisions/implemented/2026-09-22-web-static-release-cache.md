# 发布后旧静态资源导致聊天页白屏

状态：implemented
类型：bug-fix
Owner：docker/nginx/default.conf

## 问题
发布替换前端镜像后，已打开的浏览器继续引用旧哈希脚本。线上访问日志中的 user-DLBtWj2T.js 已不在新镜像内；实际 HTTP 响应为 200、text/html，内容是 SPA 入口。错误资源被缓存后，刷新仍可能白屏。真实管理员账号在全新浏览器中访问新版本正常，确认故障发生于跨版本资源加载。

## 决策
页面入口返回 Cache-Control: no-store。/assets/ 使用独立文件查找，缺失资源返回 404，并设置 no-cache，使旧缓存需要重新验证。此修复不改认证、消息或任务执行逻辑。

本次发布镜像包含当前构建与上一正式版本的哈希资源，恢复仍持有旧入口的浏览器。部署时从上一镜像提取 assets，仅合并哈希资源，保留当前 index.html；不能用旧入口覆盖新入口。标准 docker/web.Dockerfile 尚未自动保留旧资源；本次为手工组装兼容镜像。后续发布必须重复合并上一版资源，才能支持尚未刷新的页面，此项仍是人工发布约束。缓存头本身无法修复已经打开的旧页面所引用的缺失脚本。

## 替代方案
仅要求用户清空缓存不能恢复已打开页面；仅设置入口不缓存也不能补回已删除文件，因此本次同时补回旧资源。
## 后果
保留静态文件增加镜像体积，不包含用户附件或认证信息。此变更不加入自动刷新，避免丢失未发送内容。

## 验证
修复前实际旧脚本请求得到 HTML，是负向复现依据。发布前后用真实 HTTP 核对旧脚本内容类型、缺失脚本 404、入口 no-store 和脚本 no-cache；使用真实账号浏览器验证 /chat、/chat/ducha。不会发送模型请求或修改业务数据。

候选镜像 nginx -t、上述五项 HTTP 检查通过。真实管理员账号的 /chat 与 /chat/ducha 页面标题区域可见且无 pageerror；文档构建和工程契约检查通过，Linux 工程检查器单元测试 62 项通过。本机无 Docker，未运行要求的后端全量测试；未改动后端代码。通过 nginx 临时提供上一版入口、使用真实脚本与 API，确认旧入口也能恢复聊天页且无 pageerror；验证完成后删除临时入口。
