# 正式文书逐环节移交与归档

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/formal_document_service.py

## 问题

会话附件缺少正式确认、跨人员办理和归档查询语义。用户要求独立上传正式文书，按管理员配置的人员、角色和部门逐环节移交，可退回补正及保留新版，也可直接归档。

## 决策

提供当前工作区内的文书中心，以及超级管理员设置中的文书流程。采用有序接收步骤，创建时保存流程快照；指定人员与角色/部门条件取并集，角色与部门同时填写时取交集。提交时将符合条件的有效用户固化为接收人；历史参与人保留读取权限，未来步骤在收到前不可见。超级管理员可查看全部记录，但仅当前办理人可执行办理动作。直接归档默认仅提交人和超级管理员可见；流程可额外配置归档读者。

PostgreSQL 拥有文书状态、版本清单和追加流转记录。私有对象存储保留原文件，下载每次由后端鉴权；不会公开对象地址。行锁与版本号共同防止重复提交。文件上传不覆盖旧版；每次移交要求确认并显式选择当前正式文件清单。退回须填写原因，最终归档后只读。配置删除不影响历史流程。

## 替代方案

直接共享会话附件无法表达正式版本和办理责任。通用工作流引擎会引入分支、会签及执行器，超出当前有序办理需求。

## 后果

实际接收人是提交时的快照，随后部门或角色变动不撤销已授予的文书读取权限。当前版本不提供会签、电子签章或外部通知。新增表需要迁移器完成后统一更新 API 与 worker 所需 schema 版本。

配置由超级管理员维护，部门管理员作为被指定的办理人参与流程。文件限制为单个 10MB、每份文书最多 100 个版本文件；文件清单明确区分历史上传与本次正式确认。对象上传后数据库 commit 结果未知时保留对象，避免删除可能已提交的版本；孤立对象不会通过下载接口暴露。首次创建使用请求 UUID 与事务锁防重复，业务动作使用行锁和 revision。

## 验证

独立 PostgreSQL、真实 HTTP 及私有 MinIO 验证上传原字节、顺序提交、退回后新版与旧版保留、最终只读、未来环节不可见、并发重复提交拒绝、私人直接归档和通用配置入口拒绝内部配置。测试由 `backend/test/integration/api/test_formal_documents_http.py` 拥有。

`backend/test/integration/api/test_formal_document_migration.py` 在独立数据库建立 v9 结构及真实版本记录，通过子进程执行完整迁移器两次，重新查询 v10 版本行、三张新表、原有部门与升级后文书。迁移分支、manager 和 OCR 配置单元测试与 HTTP 集成合计 40 项通过；完整迁移器另 1 项通过。

前端 lint、404 项 Node 单元测试、Vite build 与 docs build 通过。真实浏览器使用隔离 API fixture 验证草稿、上传、显式确认、归档只读、配置保存及 1280/1920/390 宽度和深色；这些页面证据不替代上述真实后端集成测试。Linux 工程契约单测 62 项通过；Windows 执行存在既有平台路径差异。

完整后端单测未通过：隔离 Linux 验证副本的 `scripts/init.sh` 使用 CRLF，343 项通过后 shell 初始化检查失败；完整运行在运行链测试长时间停留后终止。配置单测使用 SQLite 类型变体建表，生产查询使用 PostgreSQL JSONB。本功能不声称仓库全量 gate 通过，部署仍需独立停机迁移与上线检查。
