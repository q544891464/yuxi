# Basic 数字员工平台首轮产品整改执行计划

状态：proposed
类型：feature
Owner：web/src/views/AgentView.vue

## 问题

[产品审查](../../basic-product-review.md)显示，Basic 的现有能力需要形成容易开始、能够找回、结果可核对的用户流程。首轮解决四个问题：无评价显示满分；新用户缺少任务示例；创建员工后还需发现能力配置入口；工作进度与成果分散。计划面向产品、设计、前后端实施者及验收人员，前置知识为现有员工配置、会话、项目、Request/Run 与资源权限模型。

起始基线为 `basic@9dd2ceab`，导航拆分已经实现，相关能力纳入回归。工作包 1 的统计与任务结果修复已落地，当前事实与证据见[满意度与后台任务结果决策](../implemented/2026-10-22-dashboard-task-results.md)；其余工作包仍为 `Not run`，本整体提案保留 proposed。源码事实与职责继续由各模块拥有，本计划不引入独立的主张编号或运行状态登记。

## 提案

首轮目标是让普通用户完成“选员工、理解任务、提交、离开后找回、查看成果”，让配置人员区分“已保存、配置检查结果、真实试运行结果”，让统计和后台任务显示有依据的结果。默认面向企业内部使用；只使用隔离账号、合成资料和独立运行环境验证。

非目标为完整发布版本系统、通用表单或流程画布、企业消息渠道、组织审批策略、团队项目权限、记忆编辑、成果协作与新的业务采纳状态。它们保留在产品审查的后续方向。首轮不改变 FIFO、worker ownership、运行重试、审批执行、资源 ACL 或个人空间边界。现有 API 的消费者、部署约束和历史数据继续纳入兼容检查。

### 实现方案

四个工作包分别在统计读模型、员工入口、配置写入和会话读模型处闭合。界面复用现有路由、表单、Request/Run 查询和成果预览；需要新增的摘要由 service 组织、repository 按当前用户和资源权限查询。HTTP 路由负责认证与装配，不在前端跨用户拼接数据，也不创建第二套任务执行引擎或持久状态机。

员工实例继续使用现有 Agent 记录。创建接口已有 `config_json` 接口能力，创建界面应复用后端 schema 和现有配置组件，禁止复制一份配置规则。未保存输入先保留在表单；保存后用当前创建者可访问的普通会话执行明确发起的试运行。保存与试运行分别显示结果，不增加发布状态字段，也不在用户填写表单时自动调用模型。

“我的工作”一期采用按会话汇总的只读入口，关联现有普通请求、顶层 Run 与定时运行来源。一条会话有多个请求时同时显示运行、排队与待处理信息，详情按既有 request/run 关系展开。数据来自持久事实，刷新和重新登录后可恢复；后台知识处理继续由独立入口负责。

### 执行顺序与交付物

以 [StaffDeck 对照分析](../../basic-product-review.md#staffdeck-对照后的迭代取舍)中的岗位表达、配置过程与工作连续性为本轮参照。四个工作包分开审阅和交付；顺序表示优先级与依赖，不承诺未经排期的日历日期。负责人在启动各包时落实到具体成员，下表先明确承担职责的角色。

| 顺序 | 工作包与建议规模 | 负责角色 | 交付物与进入下一步的条件 |
|---|---|---|---|
| 准备 | 固定验证基线，小 | 产品、测试、环境维护者 | 记录实际 HEAD、隔离环境和测试账号角色；回归已实现导航；选定两个员工、合成材料与预期交付样例 |
| 1 | 统计与任务结果口径，中 | 后端、前端、测试 | 零评价与真实零分可区分，后台知识处理结果可核对；相关 HTTP、数据库和 DOM 证据通过 |
| 2 | 首次任务与员工能力说明，中 | 产品、设计、前端 | 两个预置员工各有经审核的示例，草稿可编辑；无权限资源不被宣传为可用能力；通过浏览器验证 |
| 3 | 创建、检查与试运行，中 | 前后端、产品、测试 | 新员工保存完整配置、显示可处理的问题、能显式进入试运行；以第 2 包样例验证，不把保存当作试运行成功 |
| 4 | 我的工作最小入口，大 | 前后端、测试 | 当前用户跨员工找回会话、排队和待处理事项，正确打开对应成果；通过权限、恢复和成果归属的真实链路验证 |
| 收敛 | 普通用户试点与交付核对，中 | 产品、测试、独立 Reviewer | 执行验收矩阵与可用性任务；记录未验证范围；阻断项清零后才将对应提案转为已实现 |

第 1、2 包可在基线核对后独立推进。第 3 包依赖明确的任务样例，第 4 包依赖统一的状态文案与已有路由；若人力只够一个包，先完成第 1 包，再继续本顺序。规模仅用于区分相对工作量，实施者完成接口和交互草图后再估算工时。

### 统计与任务结果口径

整体及员工满意度在评价数为零时返回明确的无样本值，建议为 `null`，页面显示“暂无评价”和样本量；有评价且全部为差评时保留 `0%`。后端 `dashboard_repository.py` 拥有聚合口径，前端 `StatsOverviewComponent.vue` 及员工统计消费者负责无数据展示；改动前核对响应契约和所有消费者，避免空值经默认转换重新成为分数。评价样本数沿用现有有效反馈统计口径，不将所有消息数作为分母。

后台任务入口明确标为知识处理等后台工作。`TaskCenterDrawer.vue` 展示所选任务涉及文件的真实处理结果、失败原因与返回知识库的入口。任务结束与文件全部成功分别表达；无法从任务关联数据确认的文件结果显示“待核对”，不能用当前知识库总量冒充该次任务结果。如果同一文件后续被重试，显示当前文件状态及其更新时间，明确它与本次任务历史结果的区别。

先交付满意度修复，再交付后台结果表达。后者由现有 task API 和知识文件持久状态提供事实，不扩展 Task 状态机；只提供已有页面的处理入口，新增自动重试不在本包范围。验收须同时覆盖零样本、全差评、混合评价，以及任务结束但部分文件失败、后续重试、关联结果不可用的情形。

### 首次任务与员工能力说明

先覆盖智能助手和深度研究两个预置员工，每个提供最多三个由产品与业务负责人审核的示例。每个示例回答“适用任务、需要的材料、预期交付”，例如材料摘要、文档整理、资料对比；依赖检索或文件生成的示例须经过实际能力核对。`EmployeeSquareView.vue` 呈现用途，`ChatWelcome.vue` 提供开始任务的入口；说明与示例的展示逻辑在现有 `digitalEmployees.js` 旁维护，不引入可编辑模板市场或新的业务表单引擎。

首轮示例仅适用于已核对配置的预置员工，展示时依据员工配置和当前用户可访问资源过滤。员工不存在、配置被改动或依赖不可用时，隐藏不适用的示例并解释限制；自建员工展示其已有描述和通用输入提示，不按名称猜测能力。示例插入当前员工的草稿，由用户编辑并明确发送；已有草稿时先预览并让用户选择保留或替换，切换员工不能带错草稿或自动发消息。

欢迎页以任务说明替代资源数量主视觉；需要保留的资源统计标明“当前账号可访问”，员工可用能力则依据有效配置与权限呈现。用户资源多于员工启用资源、普通用户无管理权限、空账号和被删除的默认员工都必须有可理解的状态。消费界面统一使用数字员工等业务用语，高级设置保留 Agent、MCP 等必要技术名称。知识库与技能导航沿用已提交实现，只验证旧深链接、直接刷新与权限路径。

### 创建、检查与试运行

新建员工提供“用途与职责 → 能力配置 → 检查与保存 → 试运行”的顺序。形象保持可选，标识和后端选择收进高级设置并保留合法默认值。`AgentEditModal.vue` 在创建时也装配 `AgentRuntimeConfigForm.vue`，通过现有后端 schema 生成配置，向已有创建接口提交 `config_json`。保存失败保留用户输入，成功后回读实际配置并显示当前访问范围。

配置检查至少覆盖模型配置缺失、已选资源不可访问、知识库与 `knowledge-base` 技能的依赖关系。问题显示原因和定位设置的操作；后端 `agent_config_service.py` 与 repository 继续执行配置规范化和资源授权。保存阶段不主动请求外部模型验证网络，界面分别展示“已保存”“配置需处理/静态检查通过”“试运行未执行/执行结果”，静态检查通过不保证模型可用或回答正确。

试运行由创建者明确点击，进入绑定该员工的普通会话；使用合成资料，遵守既有审批与副作用边界，展示任务结果、错误和实际成果。保存时维持当前仅本人可见的默认值，共享由有权限者明确操作。首轮仅连通新建流程，既有共享员工的隔离草稿与正式发布属于后续版本方案；不能把对共享配置的直接修改包装为无影响试验。

### 我的工作最小入口

在主导航增加“我的工作”，一期只汇总当前用户有权查看的会话。列表显示标题、所属员工、更新时间、进行中的运行、排队数量、待处理提示与可用成果入口；支持按员工筛选和分页，空状态链接到员工广场。工作列表允许跨员工检索，聊天侧栏继续只显示当前员工会话，两者查询状态分开维护，避免破坏员工隔离和默认员工入口。

复用 `threadApi` 和会话读取链路；新增摘要字段由 `conversation_service.py` 组织，`conversation_repository.py` 及 Run/Request 的 repository 按当前用户和资源可见性查询。列表摘要使用批量读取，不为每行分别请求运行、队列和文件接口。定时任务已有会话时标明来源并链接原记录，尚未产生会话的计划仍由定时任务页管理；知识解析、索引和评估不混入员工工作列表。

状态文案区分排队、执行中、需处理和执行结束，失败、取消仍显示真实结局；同时存在排队与待审批时分别呈现。Run 执行成功只表示该次执行结束，成果是否满足业务要求由用户判断。点击“继续处理”返回绑定员工及会话，沿用现有审批、回答和恢复入口。首轮不从列表直接触发重试、取消或批量操作。

成果只展示所属 request/run 的实际输出；同一会话多个 Run 必须能分辨，失败 Run 的部分成果不能冒充成功交付。纯文本任务可以没有文件，文件失效或访问被收回时给出明确结果。预览、下载与保存复用 `AgentArtifactsCard.vue` 和 `artifact_service.py` 的权限与文件边界；文件内容被后续覆盖时不承诺不可变版本。详情退出、刷新、重新登录后应从持久状态恢复同一工作记录。

## 替代方案

| 方案 | 收益 | 未采用或限定范围的原因 |
|---|---|---|
| 只调整文案与菜单 | 交付快，容易回退 | 无法修正统计语义、配置写入断点和工作找回，不能覆盖本轮验收 |
| 一次建设岗位市场、SOP 画布、版本发布与多渠道 | 产品覆盖面广 | 引入多个新的状态、维护者与兼容承诺，缺少部门试点证据；分别保留为后续提案 |
| 新建独立业务任务表与执行引擎 | 可以重新设计统一任务状态 | 与当前 Request、Run、scheduled occurrence 和后台任务的事实重叠，扩大一致性和迁移成本；当前需求用读取摘要即可满足 |
| 复用现有执行链路，补齐入口与结果表达 | 四个工作包可以独立验证，保留现有权限和恢复边界 | 采用；接受首轮没有通用模板编辑、共享员工草稿、业务采纳状态和成果版本的限制 |

### 验证执行与放行

后端 HTTP 验证在隔离 Compose、真实 PostgreSQL 下执行，涉及队列和成果归属时补齐实际 API、worker 与最终文件的 E2E。前端执行 lint、相关 unit、build 和真实浏览器；已有 `web/test/browser/employeeSidebar.js`、`managementNavigation.js` 可验证部分页面语义，其中替身 API 不能替代真实后端权限及恢复验收。常用命令与环境约定以[测试规范](../../testing-guidelines.md)和[隔离环境指南](../../parallel-worktree-environments.md)为准。

定向命令从仓库根执行，先在相应文件增加本轮断言再运行；按实际改动补充上述矩阵中的其余用例：

```bash
docker compose exec api uv run --group test pytest test/integration/api/test_dashboard_router.py test/integration/api/test_agent_config_resource_authorization.py
docker compose exec api uv run --group test pytest test/integration/api/test_agent_run_result_causality.py test/integration/api/test_agent_request_queue_router.py
docker compose exec api uv run --group test pytest test/e2e/test_deterministic_agent_path_e2e.py -m e2e
```

产品验收使用提前人工审阅的合成材料、任务说明和成果检查项。邀请 5–8 名目标业务用户，给予任务目标而不讲操作路径；建议门槛为至少 80%（人数向上取整）在 5 分钟内完成首次有效提交，并在离开页面后 1 分钟内找回指定已完成任务及其正确成果。模型执行耗时单独记录，不计入操作时间；小样本用于发现可用性问题，不作整体用户效率提升的统计承诺。

任何跨账号泄漏、错员工提交、错 Run 成果、已有草稿丢失、假满分或假成功都阻断相应工作包放行。Reviewer 依据完整需求、最终 diff、测试与未验证范围独立审查；证据缺失时保留 proposed，不能用文档构建、HTTP 200 或已有用例通过替代。各工作包记录自己的命令与结果，整体完成后再按[决策生命周期](../README.md)收敛本提案。

## 风险

- 环境与证据：真实 HTTP、worker 和文件验收需要隔离 Compose；模型样例需要部署者提供的可用模型与受控资源。工作包 1 已使用远端隔离 Compose 完成对应验证，其余范围仍需按各自风险补齐。环境或凭据缺失时记录 `Not run` 及影响，文档落档不构成任何产品链路已验证。
- 示例与能力漂移：预置员工可被修改，示例依赖也会变化。产品负责人维护任务内容，配置与权限决定能否展示；不承诺未经实际验证的检索、联网或文件交付能力。业务样例维护成本随模板数量增加，首轮限定两个员工。
- 状态与权限：跨员工个人列表容易误写为跨用户工作台，历史文件状态也容易被当作本次运行结果。repository 的用户过滤、request/run 因果关系及文件边界是放行重点；当前实现无法证明的摘要字段先显示未知，不补造成功值。
- 兼容与回退：满意度空值可能影响既有 API 消费者，实施前核对契约并同步展示端。四个工作包分别交付；回退页面和摘要接口不删除已保存员工、请求或成果。首轮不计划新业务表或迁移，若实现发现持久化变更必要性，须在 owning proposal 说明消费者、迁移与回退后再实施。
- 范围与价值：岗位流程、版本发布和企业渠道仍有差距，本轮只验证起步与交付体验。若试点显示用户主要受模型质量或知识资料质量阻碍，记录任务样本与独立判断，优先修正相关 Owner；不以增加入口数量替代效果改善。
